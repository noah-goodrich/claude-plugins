# The AI Efficiency Trap: Why I Built a Tool to Tell Cursor What to Test

Last month, I watched an engineer on my team commit 48 new unit test files generated by Cursor in under ten minutes. Pytest ran green. Our repository line coverage jumped from 61% to 89%. Management was thrilled; the velocity dashboard looked like a hockey stick.

Forty-eight hours later, a silent data corruption bug slipped into our core billing pipeline. 

A PySpark transformation responsible for late-arriving event reconciliation had silently dropped records with null partition keys during a structural join. Cursor had generated twelve tests for that module. All twelve asserted that our mock clients returned HTTP 200s, that our custom logger formatted strings correctly, and that our basic dataclasses initialized with default values. It had tested the mechanical scaffolding of the pipeline while completely bypassing the algorithmic risk.

This is the AI efficiency trap. LLMs are exceptionally good at writing low-value, boilerplate unit tests that maximize code coverage metrics without validating business-critical logic. 

To fix this, I stopped letting Cursor decide what to test. Instead, I built a Python-based static analysis tool that scores our codebase by algorithmic complexity, data mutation density, and blast radius—producing a deterministic priority queue that directs Cursor directly to the functions that can actually break production.

## The Illusion of 90% Line Coverage

Data pipelines have an asymmetric failure profile. If an API client wrapper fails, it raises an exception and the DAG fails loud and early. But if a stateful window aggregation, a dynamic schema casting function, or an out-of-order deduplication loop fails, it fails *quietly*. It writes malformed parquet files to your S3 bucket, corrupts downstream metrics, and wakes you up three weeks later during financial close.

When you feed a prompt like *"Write comprehensive unit tests for `pipelines/transforms/`"* into an AI assistant, the LLM optimizes for syntactic completion:

1. **Path of Least Resistance:** It writes tests for pure, trivial methods—simple filters, string formatters, schema wrappers—because their input-output contracts are simple to synthesize without deep context.
2. **Mock-Heavy Hallucinations:** When faced with complex distributed dataframes or deeply nested state dictionaries, it creates aggressive mocks that mock out the very behavior (e.g., Spark catalyst optimization quirks, memory pressure, null-handling semantics) that causes pipeline failures.
3. **Vanity Coverage:** You get high line coverage, but branch and boundary coverage on critical transformation paths remain functionally zero.

We didn't need *more* tests. We needed tests targeted explicitly at high-entropy code paths.

## Designing the Code Risk Score (CRS)

To guide Cursor systematically, I wrote an internal CLI tool named `test-lens`. It inspects our Python codebase using the standard `ast` module and computes a **Code Risk Score (CRS)** for every function and class. 

The score is calculated based on three specific vectors:

$$\text{CRS} = (\text{Cyclomatic Complexity} \times W_c) + (\text{Data Transformation Density} \times W_d) + (\text{Blast Radius} \times W_b)$$

### 1. Cyclomatic Complexity ($W_c$)
We parse the Abstract Syntax Tree (AST) to count decision points: `If`, `For`, `While`, `Try`, `BoolOp`, and comprehensions. A function with nested conditional branches around dynamic partition filters has a high cyclomatic complexity and requires boundary condition tests.

### 2. Data Transformation Density ($W_d$)
For a data engineer, structural operations carry more risk than I/O operations. We traverse AST call nodes and attribute lookups to identify:
* Windowing operations (`over()`, `partitionBy()`)
* Structural mutations (`explode()`, `pivot()`, `join()`, `groupBy()`)
* Type casting and regex extractions (`cast()`, `when().otherwise()`, `regexp_extract()`)

### 3. Blast Radius ($W_b$)
We evaluate the dependency graph. A utility function imported by twelve downstream DAGs has a significantly higher blast radius than a one-off export script. We calculate fan-in (incoming references) across the repository.

## The Implementation: Building the AST Risk Scorer

Here is a simplified version of the AST visitor engine at the core of `test-lens`:

```python
import ast
from dataclasses import dataclass
from typing import List

TRANSFORMATION_KEYWORDS = {
    'join', 'groupBy', 'pivot', 'explode', 'window', 
    'withColumn', 'when', 'otherwise', 'repartition'
}

@dataclass
class FunctionRiskProfile:
    name: str
    file_path: str
    line_number: int
    cyclomatic_complexity: int
    transformation_density: int
    risk_score: float

class PipelineRiskVisitor(ast.NodeVisitor):
    def __init__(self, file_path: str):
        self.file_path = file_path
        self.profiles: List[FunctionRiskProfile] = []

    def visit_FunctionDef(self, node: ast.FunctionDef):
        complexity = 1
        transformations = 0

        for child in ast.walk(node):
            # Calculate cyclomatic complexity
            if isinstance(child, (ast.If, ast.While, ast.For, ast.ExceptHandler, ast.comprehension)):
                complexity += 1
            elif isinstance(child, ast.BoolOp):
                complexity += len(child.values) - 1

            # Identify data transformation mutations
            elif isinstance(child, ast.Call):
                if isinstance(child.func, ast.Attribute):
                    if child.func.attr in TRANSFORMATION_KEYWORDS:
                        transformations += 1

        # Composite score calculation
        risk_score = (complexity * 1.5) + (transformations * 2.0)

        self.profiles.append(
            FunctionRiskProfile(
                name=node.name,
                file_path=self.file_path,
                line_number=node.lineno,
                cyclomatic_complexity=complexity,
                transformation_density=transformations,
                risk_score=risk_score
            )
        )
        self.generic_visit(node)
```

Running this across our repository generates a deterministic list of functions ordered by priority. 

Instead of showing a flat coverage percentage, `test-lens` highlights files where test coverage is inversely proportional to complexity:

  - Risk Score: 1.5 (DO NOT TEST FURTHER)

## Feeding Structured Context to Cursor

Once `test-lens` identifies high-risk targets, it outputs structured test prompts directly to `.cursor/prompts/` or directly into the clipboard formatted for Cursor's Composer mode.

Instead of generic instructions, the generated prompt feeds Cursor explicit boundary constraints:

```markdown
Target Function: `src/transforms/reconcile.py::resolve_split_invoices` (Lines 45-112)
Target Risk Score: 49.0
Identified Complexity Nodes:
  - Nested conditionals on line 62 (`None` check on parent invoice)
  - PySpark Window operation on line 78 partitioned by `account_id` ordered by `event_timestamp`
  - Explode operation on array column `line_items`

Instructions:
1. Write a parametrized pytest suite using `chispa` or `pytest-mock` for PySpark.
2. DO NOT write happy-path-only tests.
3. Explicitly construct test DataFrames for these 3 edge cases:
   a. Input contains out-of-order events with identical timestamps.
   b. `line_items` array is empty or contains a `null` literal.
   c. Multiple parent invoices exist for a single child transaction.
4. Verify schema preservation and null-safety across all branches.
```

By constraining the context window to structural risk points, Cursor stops hallucinating mock API clients and starts writing high-density test matrices targeting real pipeline failure modes: null pointer exceptions, duplicate aggregation frames, and schema drifts.

## The Results: Signal Over Noise

Shifting from naive coverage targets to an AST-driven test priority model changed our development workflow:

* **CI Runtime Dropped 40%:** We deleted hundreds of brittle, auto-generated tests that mocked built-in library functionality without testing business logic.
* **True Defect Detection:** Within two weeks of targeting high-risk functions, Cursor-generated property tests caught two edge-case aggregation bugs before they reached staging.
* **Deterministic Reviews:** Pull request reviews no longer involve debating coverage percentages. If a PR touches a function with a Risk Score $> 25$, the author must show corresponding tests covering the decision nodes flagged by `test-lens`.

AI coding tools like Cursor are force multipliers, but without deterministic guardrails, they multiply low-value code just as fast as high-value architecture. Directing AI toward structural complexity turns it from a vanity coverage generator into a rigorous testing engine.
